126. How do you type useReducer?

Define state and action types.

type State = {
  count: number;
};

type Action =
  | { type: "increment" }
  | { type: "decrement" };

function reducer(
  state: State,
  action: Action
): State {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };

    case "decrement":
      return { count: state.count - 1 };
  }
}

🧠 Easy Memory:

Type State + discriminated-union Action.

134. How do you type fetch() responses?

For safer applications, validate unknown data at runtime.

🧠 Easy Memory:

Where:

function isUser(value: unknown): value is User {
  // runtime checks
  return true;
}

🧠 Easy Memory:

External data is untrusted until runtime validation proves its shape.

Coding 1 — Generic Identity
Question

Coding 2 — Generic API Response
Question

Create ApiResponse<T> supporting:

ApiResponse<User>
ApiResponse<Product>
ApiResponse<Order>
Answer

  success: boolean;

Coding 3 — Implement MyPartial<T>
Answer
type MyPartial<T> = {
  [K in keyof T]?: T[K];
};

Example:

interface User {
  id: number;
  name: string;
}

type PartialUser = MyPartial<User>;

Becomes conceptually:

{
  id?: number;
  name?: string;
}

🧠 Memory:

Partial = map every key + add ?.

Coding 4 — Implement MyPick<T, K>
Answer
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};

Example:

interface User {
  id: number;
  name: string;
  email: string;
}

type Preview = MyPick<User, "id" | "name">;

🧠 Memory:

Pick = map only selected keys.

Coding 5 — Implement MyReadonly<T>
Answer
type MyReadonly<T> = {
  readonly [K in keyof T]: T[K];
};

🧠 Memory:

Readonly = map every key + add readonly.

Coding 6 — Implement MyExclude<T, U>
Answer
type MyExclude<T, U> =
  T extends U ? never : T;

Example:

type Status =
  "success" | "error" | "loading";

type Result =
  MyExclude<Status, "loading">;

Result:

"success" | "error"

🧠 Memory:

Exclude = if T matches U, remove it with never.

Coding 7 — Implement MyReturnType<T>
Answer
type MyReturnType<T> =
  T extends (...args: any[]) => infer R
    ? R
    : never;

Example:

function getUser() {
  return {
    id: 1,
    name: "Aravind"
  };
}

type User = MyReturnType<typeof getUser>;

🧠 Memory:

ReturnType = function → infer its return value.

Coding 8 — Type-safe get
Question

Given:

const user = {
  id: 1,
  name: "Aravind",
  age: 25
};

Allow:

get(user, "name");

but prevent:

get(user, "xyz");
Answer
function get<T, K extends keyof T>(
  obj: T,
  key: K
): T[K] {
  return obj[key];
}

Usage:

const name = get(user, "name");

The result is inferred as:

string

This fails:

get(user, "xyz"); // Error

because "xyz" isn't part of keyof typeof user.

🧠 Memory:

K extends keyof T = key must belong to the object.

🧠 Most Important "WHY?" Questions
1. Why is unknown safer than any?

Because unknown forces you to narrow the value before performing operations, while any disables most type checking.

🧠 Memory:

unknown requires proof; any requires trust.

2. Why does TypeScript use structural typing?

Structural typing makes TypeScript flexible and compatible with JavaScript's object-based programming model.

Two objects can be compatible if their required structures match.

🧠 Memory:

TypeScript cares about what an object has, not what it is called.

3. Why does keyof return a union?

An object can have multiple possible property keys. Therefore:

type User = {
  id: number;
  name: string;
};
keyof User

becomes:

"id" | "name"

The union represents the set of valid keys.

🧠 Memory:

keyof = all possible keys → union.

4. Why do we need generics?

Generics let us create reusable functions, classes and types without sacrificing type information.

🧠 Memory:

Generics = reusable code + type safety.

5. Why use extends in generics?

To constrain a generic to types that satisfy a requirement.

function getId<T extends { id: number }>(obj: T) {
  return obj.id;
}

🧠 Memory:

extends in generic = minimum requirement.

6. Why does never exist?

It represents impossible values and functions that don't complete normally.

It is especially useful for exhaustive checks.

🧠 Memory:

never represents "this cannot happen."

7. Why are conditional types useful?

They allow types to change based on another type.

type IsString<T> =
  T extends string ? true : false;

They enable powerful reusable type transformations.

🧠 Memory:

Conditional types = if/else at the type level.

8. How does type narrowing actually work?

TypeScript analyzes checks such as:

typeof
instanceof
in
=== 

and control flow to eliminate impossible types.

🧠 Memory:

Narrowing = runtime evidence → more precise compile-time type.

9. Why can TypeScript not validate API responses at runtime?

TypeScript's types are erased from the generated JavaScript.

The server sends runtime data, which TypeScript doesn't automatically validate.

For example:

const user = data as User;

doesn't verify that data actually matches User.

🧠 Memory:

TypeScript checks your code, not external runtime data.

10. Why are type assertions potentially dangerous?

Because assertions don't perform runtime validation.

const user = data as User;

If data is malformed, TypeScript won't automatically detect it at runtime.

🧠 Memory:

Assertion ≠ validation.

11. Why use satisfies instead of as in some cases?

satisfies verifies that an expression conforms to a type while preserving useful inference.

const config = {
  port: 3000,
  environment: "production"
} satisfies Config;

An assertion:

const config = value as Config;

mainly tells TypeScript to treat the value as that type.

🧠 Memory:

as says "assume"; satisfies says "check".

12. Why can TypeScript allow some seemingly unsafe assignments?

TypeScript is designed around JavaScript compatibility and uses structural typing, inference, assignability rules, and some intentional flexibility.

It is not a formal proof system guaranteeing that every runtime operation is safe.

🧠 Memory:

TypeScript improves safety; it doesn't guarantee runtime correctness.

13. What happens to TypeScript types at runtime?

They are generally erased when TypeScript is compiled to JavaScript.

For example:

const age: number = 25;

becomes roughly:

const age = 25;

The number annotation doesn't exist at runtime.

🧠 Memory:

Types disappear; JavaScript remains.

14. Does TypeScript provide runtime type safety?

No, not by itself.

TypeScript provides compile-time type checking.

Runtime data from APIs, users, files, databases, etc. may still be invalid.

For runtime validation, you need explicit checks or a runtime validation library.

🧠 Memory:

TypeScript = compile-time safety, not automatic runtime validation.

15. How would you validate unknown API data at runtime?

Treat the data as unknown and validate its structure before using it.

For example:

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) {
    return false;
  }

  const user = value as Record<string, unknown>;

  return (
    typeof user.id === "number" &&
    typeof user.name === "string"
  );
}

Then:

const data: unknown = await response.json();

if (isUser(data)) {
  console.log(data.name);
}

For larger applications, runtime schema-validation libraries can automate this pattern.

🧠 Memory:

External data → unknown → validate → trusted type.
